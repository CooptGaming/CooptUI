13dWhat goes where — the rule that keeps both bars from turning into the old 16-button grid
Top bar — reports
Things you read without clicking. Never grows or shrinks; segments swap content inside fixed slots.
  • plugin / macro state
  • bags, weight, plat
  • what a sale would fetch
  • live loot or sell progress + its stop button
  • buffs, songs, aura, expiries
  • XP, AA, script value
  • session total
Hover any of them for the detail popover (12b).
Bottom bar — commands + chat
Things you click on purpose. This is where the Command Center goes to die.
  • every CoOpt window, lit when open
  • native game windows: Inventory, Merchant, Actions, AA
  • layout presets
  • Settings
  • chat: collapsed line, peek, or hidden
The old Command Center window is retired; /itemui center just focuses this bar.
Middle — the actual work
Anything with a table, a grid or a paper doll stays a window.
  • Inventory, Bank, Equipment
  • Item Display, Augments, Aug Utility
  • AA, Reroll, Mythics
  • Settings and the rules screens
Placed by zone (10a), between the two bars — which are subtracted from the work area first, so a window can never hide under one.
Nothing lives on bothIf it's on a bar it is not also a button inside a window, and vice versa — one home per control, so there's no "which one do I press". A verb only appears when it worksAuto Sell is greyed until a merchant is open; Stop only exists while something runs. No dialog ever tells you "open a merchant first". Both bars are optionalTop / bottom / both / neither, per layout preset. With both off you get today's behaviour: windows and slash commands only. Screen budget38 + 40px of a 1368px screen is under 6%, and it buys back the Command Center window, the chat windows and the hub's 12-button toolbar.

12cWhat it takes in MQ's ImGui — and the four rules that keep it stable
All three behaviours are ordinary ImGui
Live segmentsThe bar is redrawn every frame anyway, so a segment is just if lootRunning then … else … end reading the same uiState the Loot window already reads. No new plumbing — loot_ui.lua is already tracking corpse counts, totals and the mythical alert. Hover popoverNot a tooltip — tooltips can't take clicks. Use a second borderless window positioned under the segment with NoFocusOnAppearing + NoNav + AlwaysAutoResize, opened when the segment is hovered and closed when neither the segment nor the popover is hovered (with a ~250ms grace so the mouse can travel between them). Buttons inside it work normally. Click to openregistry.toggleWindow(id) — exactly what the Command Center buttons already call.
The four rules
Fixed slot widthsEach segment reserves the width of its widest possible string, measured once at startup with CalcTextSize and cached. Content changes inside the slot; the slot never resizes. This is the whole anti-jitter story. Never query per frameSegments read cached values only — the scan service and sell_status.lua already refresh on their own cadence. A dock that called TLOs every frame would cost more than the rest of the UI combined. One clock, coarseTimers and countdowns update on a 250ms tick, not per frame: no flicker, and “8s / 7s / 6s” reads better than a blur of decimals. Nothing steals inputThe dock takes NoFocusOnAppearing and never calls SetWindowFocus, so clicking a segment doesn't pull focus away from the game. Popovers close on mouse-out; only a middle-click pin keeps one alive.
The one genuine limit
An ImGui window swallows mouse input where it sits — the strip is a thin band, but a popover hanging over the game world will eat a click meant for the world underneath while it's open. Hence: popovers only open on deliberate hover, close the moment the mouse leaves, and never appear on their own during combat.

10aZones, not coordinates — every window opens into the next free slot around the hub, never on top of another
Screen zones
The hub anchors; everything else fills outward in a fixed order, clamped to the screen.

Slot order per window is declared once in the registry (zone = "R1", next to buttonWidth and layoutKeys). Opening a window walks its zone list, takes the first slot that is free and fully on-screen, and only then falls back to the old hub-relative offset.
Rules that make it feel deliberate
  • Never overlap on open. If every slot in the zone is taken, the window opens as a tab inside the occupant rather than on top of it.
  • Off-screen is impossible. Placement clamps to the work area, so a window opened on a 4K desktop and reopened on a laptop still lands fully visible.
  • Move once, keep it. The moment you drag a window it becomes “user placed” and stops auto-slotting — until you press Re-tidy.
  • One re-tidy button. In the dock overflow and Settings: puts every open window back into its zone in one frame.
  • Nothing hides the dock. Its strip is subtracted from the work area before any placement is computed.
This is an extension of what main_window.lua already does — it computes Equipment at hubX − eqW − gap and friends on first open — turned into a table instead of hardcoded arithmetic, plus an occupancy check.
10bMagnet edges — windows snap to the hub and to each other, then move as one
While dragging
Within 12px of an edge, a guide appears and the window lands flush with a 4px gutter.

Implementation is small: after ImGui.GetWindowPos, compare against the rects of the other open windows; if a pair of edges is within the threshold, write the aligned position through SetNextWindowPos on the following frame and record the attachment.
Once snapped they behave as a unit
  • Drag the hub — everything attached to it travels with it, keeping gutters.
  • Resize the hub's right edge — the column snapped to it re-aligns instead of being covered.
  • Close a window in a snapped column and the ones below slide up to close the gap.
  • Hold Alt while dragging to ignore magnets entirely for that drag.
Stored as relationships, not pixels
The layout INI gains one line per attached window — Attach_itemDisplay=hub:right:top — so a saved layout survives a resolution change, unlike raw coordinates.

9ePane rules — what happens when you open another window, and how to keep ImGui from wobbling
One subject, many viewers
There is no “selected row” in CoOpt — left-click picks an item up. The subject here is the context target: the item you last right-clicked, exactly as Item Display is opened today. A single service owns it and windows subscribe, which is what makes “open another window” boring instead of ambiguous.
1 · you right-click a row
The context menu opens as today, and the item becomes the context target. Pane fills in. Left-click still just picks the item up; nothing about the table changes.

Nothing is lost when the pane appears
  • The pane takes width from the window, not from the table: opening it widens the window by exactly its width (and narrows it again on close). If the window is already at your screen edge, it stays put and the table scrolls horizontally instead — column widths never change under you.
  • Collapsed it is a 16px rail with a chevron; the last subject stays loaded, so reopening is instant and shows the same thing.
  • Everything in the pane also exists elsewhere: it is a shortcut, never the only route. Right-click menus, Item Display and the rules screens keep working exactly as today.
  • Pop-out ↗ on any pane section detaches it as its own window; the pane then shows a one-line stub with “showing in its own window · return”.
Why the old right-pane felt inconsistent in ImGui — and the four rules that fix it
Fixed pixel width, alwaysBeginChild("pane", ImVec2(paneW, 0)) with paneW read from the layout INI and clamped (240–420). Never size the pane from its content, and never let a long item name decide the layout — that is what made it jump frame to frame. Table gets the remainder onceCompute avail - paneW - splitter at the top of the frame and pass it to the table child. One measurement per frame, before anything draws. Reserve, don't reflowEmpty pane still draws its frame at full width with a muted “select an item” line, so the layout is identical whether or not something is selected. State lives outside the frameSubject, pinned flag, section open/closed and paneW live in the state module and are written to INI on change — not in ImGui's own storage. Any window can be closed and reopened without the pane forgetting.
All four are patterns the codebase already uses for the main table (layout_columns.lua, window_state.lua) — the pane just has to obey them too.

7Native-skin parity — what EQUI XML + the MQ2CoOptUI plugin can really do, and what it would look like
7aFeasibility board — read against your own code, not guesswork
The native surface has four primitives today
From services/native_bridge.lua and plugin/MQ2CoOptUI/capabilities/window.cpp.
Click inButtons declared Style_Checkbox; the bridge polls Checked() and treats any transition as one click, then un-latches ≥350ms later when the mouse is off it. Text outplugin.setText(wnd, child, str) calls CXWnd::SetWindowText — works on any child: labels, buttons, edit boxes. Without the plugin, MQ's SetText only reaches EditBoxes. State outplugin.setChecked — latch a button to show on/off without synthetic input. StructureWhole windows can be repurposed (TipWnd is already the Command Center) and tabs added as Page items (the Actions window's CoOpt tab).
Four more plugin calls buy almost everything else
Each is a thin wrapper on an eqlib class you already link against — the same pattern as setText.
setVisible(wnd, child, bool)Show/hide pre-declared controls. This is what makes a fixed XML row pool behave like a dynamic list. list.* on CListWndClear, add row, set cell text, cell colour, cell icon, read selection. Turns a native Listbox into the inventory / sell / loot table. setSTML(wnd, child, stml)CXStmlWnd::SetSTMLText — rich coloured text with item links. The right home for Item Display, Sell Preview and wizard copy. setTooltip(wnd, child, str)Today tooltips are frozen strings in XML; per-item hover text needs this.
Hard limits — design around these, don't fight them
  • Controls cannot be created at runtime. Everything is declared in XML at load, so lists become a fixed pool (say 20 rows) that you page through.
  • No per-row buttons inside a listbox. Native pattern instead: select a row, act from the button bar — exactly how the stock Merchant window works.
  • Layout is anchored at load; no reflow, no drag-to-reorder columns, no resizable column widths beyond what the XML declares.
  • EQ's five built-in fonts only, no per-frame drawing, no animation, no hover states beyond the built-in highlight.
  • A skin change is a client-side file the player must install and /loadskin coopt; every window you touch must stay compatible with the server's stock XML.
