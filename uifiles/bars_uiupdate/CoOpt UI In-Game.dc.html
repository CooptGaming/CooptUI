29zRead this first — two things the code says that change what gets built
1. Docking is not on, and nothing uses it
No DockSpace, no ConfigFlags, no dock node anywhere in itemui. Placement is already solved a different way and it is better than dock nodes for this: window_zones.lua — L1/L2 left of the hub, R1/R2 right, B1/B2 below, 6px gutter, 12px magnet, and 8px of drift marks a window user-placed so it is never moved again.
So every frame below is a zone arrangement, not a dock layout, and the pairs from 23a/23b are placement conventions plus a shared subject — not split dock nodes. That is the cheaper build and it keeps the move-once-keep-it rule you already have.
2. Much of turns 24–28 is already built
context_menu.lua already carries the four-group anatomy and quotes Rule 3 in its header. script_tracker.lua, chat_window.lua, dock_top, dock_bottom, hub_list and layout_presets all exist. Merchant and banker auto-open already work through hints.lua and main_loop.
Two names to reconcile rather than re-invent: the bundled presets are Bag session, Farming, Merchant run, Gearing up, Raid - minimal, not my Looting/Augmenting/Merchant — keep yours, I have used them below. And augments and augmentUtility are still two registered windows; 23c folds the first into the second's All tab.
How to read the frames
Everything is drawn at true pixel size for a 2554×1368 client. Bars are 30px, gutters 12px, so the work area is y 42–1326. Every window rect is stated in its caption, and every window is drawn full — the row counts you see are the row counts that fit, so density is reviewable here rather than discovered in the client.
These are not shipping defaults — they are reference sheets so each window can be built against a real neighbour. Each frame states its own column set rather than sharing one grid, because window_zones lays out per activity: a two-window job gets wide columns, a four-window job gets narrow ones.
The only universal rules: 12px on every edge and between every window, and columns sum to the viewport width. 29a is 12 + 880 + 12 + 720 + 12 with the remainder left as game. A four-window frame is 12 + 620 + 12 + 980 + 12 + 906 + 12. 1920 and 4K are the same arithmetic against a different viewport — the placer already reads it, so those are cheap once these land.
Answered and folded in: scripts are click-to-consume, so Script Tracker turns in from your bags with no NPC state (25c); the HP/HEROIC questions are settled in code; auto-open on vendor and banker is existing behaviour, so the lane in 28b reports it rather than inventing it.

A layout is bound to an action, not a name — that binding is what makes it open itself. A layout you save with no action attached is still fine; it is just shortcut-only, like Banking above.
Save is the whole feature
Ship the three actions with sensible arrangements, but treat those as starting points — the first thing anyone does is move a window. Save what's open as… writes wherever things currently sit over the chosen action. No layout editor, no preview, no drag-to-arrange screen: the game window is the editor.
Each layout owns three things: the windows and their rects, an optional action that triggers it, and an optional shortcut. Any of the three can be empty. Banking above has no trigger — it is shortcut-only, and that is a valid layout.
Shortcuts are assigned, never listed. New layouts start unassigned; picking one opens a capture field that rejects anything MQ, EQ or CustomBinds already owns, with the conflict named. ctrl+alt+<n> shown here is only a plausible-looking default.
Close everything is the row people will use daily — and it belongs here because it is a layout: the empty one.
